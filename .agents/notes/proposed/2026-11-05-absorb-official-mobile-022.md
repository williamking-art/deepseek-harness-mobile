# 从官方 0.2.2 的"移动端"变更里吸收什么（待评审）

- 日期：2026-11-05
- 来源：DSH `dsh-v0.2.2-rc.1` 发布说明（GitHub Release），以及 nightly feed 的 0.2.2-rc.1 元数据
- 状态：proposed（**待评审**，未动代码）。与 0.1.26（去掉版本限制）的关系：先把插件解绑，才能在 0.2.2-rc.1 上实测这些项

## 0. 先厘清：官方"移动端"是什么

0.2.2 的移动相关改动是 **官方 Web/桌面 UI 的响应式适配**（手机浏览器打开 DSH Web），
不是原生 App，也没有官方中转/端到端加密远程通道。原文：

> 完善手机和平板适配，优化软键盘交互、导航与窄屏布局，保持菜单和操作入口可用。

配套能力是 Web 端远程可达性：`--public-url`、绑定地址、原生 HTTPS（`--tls-cert/--tls-key`）、
远程连接默认 WebSocket 压缩、网关按调用方身份授权。

**结论**：官方解决"手机浏览器访问一台**可达**的 DSH"；我们解决"手机 App 经中转
**跨 NAT 访问**且端到端加密"。重叠在"同网/有 VPN 时的手机访问"，差异在"外网随处访问 + 通知/审批"。

## 2. 不吸收（让给官方 Web）

- 宽屏/多栏布局、右键菜单、键盘快捷键、顶部标签页等桌面交互；
- 官方 Web 的 `--public-url`/TLS 部署能力（我们继续走中继，不重复造）；
- 官方插件市场的索引/发现机制（我们有自己的 fleet 清单）。

## 3. 定位判断（历史使命是否被取代）

- **短期不被取代**：官方移动 = 浏览器 UI，前提是"能访问到那台电脑"；没有跨 NAT 中继、没有 E2E、没有原生 App/配对。
- **被吃掉的部分**：同网/有 VPN/Tailscale 时的"手机看会话"——官方会持续变好，我们不应在这里拼。
- **该守的部分**：外网随处访问（中转）、端到端加密、配对/多设备、后台通知与审批。
- **中期风险**：若官方发布官方 App 或官方中继，本插件的独立价值会大幅下降；届时应转为"官方 Web 的远程接入壳"。

## 4. 战略选项

- **A. 继续原生 App**：按上面清单吸收 P0/P1，强化远程+通知+审批，UI 自己维护。
- **B. 收缩为"接入层"**：App 内嵌官方响应式 Web（WebView/PWA），我们只保留中转隧道 + 配对 + 推送；UI 维护量骤降，原生体验变弱。
- 建议：**A 的定位 + B 的部分做法**——远程通道/通知/审批保留原生，会话与审阅类页面评估用官方 Web 承载。

## 5. 与 0.1.26 的衔接

**能在 0.2.2-rc.1 的临时环境里装上并实测**（先把"能不能跑"与"吸收清单"分开）。实测通过后再按上表排期。
